# 射频冷唤醒延迟对照（2026-10-12）

测试设备为同一 Chameleon Ultra，读卡器为 PN532/libnfc；固定槽位1、相同卡片数据、纯电池供电。每次关场8秒，再开场等待指定时间，只做一次ISO14443A SELECT。每档3次。Mocha关闭轮询；官方关闭启动动画。

官方版本使用未修改的5c99d4a源码本地构建；Mocha为1.0.0-11211b3。官方不支持Mocha扩展配置，会回退到默认设置；因此已验证测试槽卡片数据相同，但未完全匹配持久化布局，且不是交错A/B测试。

|等待时间|官方首次成功|Mocha首次成功|
|---|---|---|
|500ms|0/3|0/3|
|700ms|0/3|0/3|
|1000ms|0/3|0/3|
|1200ms|0/3|0/3|
|1500ms|3/3|2/3|

本轮显示官方关闭动画后也有明显的冷唤醒等待，不能将该延迟认定为Mocha独有回归。每档样本仅3次；1500ms少一次成功不能证明Mocha更慢。软件等待及PN532请求窗口不等于芯片就绪的精确时间，也不能推广到所有读卡器或LF设备。

## 启动计时线索

原版只读1110采用DWT CPU活动计时。受控NFC唤醒复位原因0x80000，应用累计约90ms；不能把90ms当作墙钟启动时间。

临时诊断构建使用未占用的TIMER3测量应用入口后经过时间：SoftDevice启用约298ms、后续BLE初始化约116ms、模拟入口约61ms，总计约476ms。它不覆盖引导程序及场检测，且计时器保持HF时钟可能扰动启动。约298ms与LFXO启动等待相符，但尚未独立证实。该诊断版开场等3秒仍读取失败，不能将此次失败仅归因于启动时间，也不能据此断言原版接收器卡死。

一次早期TIMER4诊断与SDK NFCT兼容处理冲突，已撤回；其后半段数据和接收结果不用于结论。临时诊断补丁和固件均不包含在本次发布产物中。

官方、Mazha及nieldk源码共有完整启动和BLE/晶振初始化流程；官方和上述第三方按动画设置在RF分支等待动画，Mocha当前RF分支已跳过动画。第三方未做同设备实机对照。

引导程序只对GPIO唤醒位或特定标志跳过CRC，未覆盖独立NFC/LF唤醒位，因此CRC仍是候选开销；未测实际bootloader耗时，不能宣称已定位根因。受误触按键、设备离场影响的reset_reason=0样本不作为正常RF延迟归因。

## 恢复与边界

测试后恢复Mocha-1.0.0-11211b3及原设置，16槽元数据、完整HF dump、LF ID和设置与备份逐项一致。未进行门禁认证或放行验证。公开记录省略设备标识、卡号和个人备份。
