# Access Trace v1.3：容量、验证及刷入边界

本实现仅修改 `firmware/mocha`。协议见 [access-trace-protocol.md](access-trace-protocol.md)。
没有修改 Bootloader、SoftDevice、卡槽格式、FDS 页数或地址。默认每次启动关闭记录，开启只在本次运行有效。

## Flash 审计

nRF52840 Flash 1 MiB，应用从 `0x27000` 开始，Bootloader 链接地址 `0xF3000`。
当前 FDS 为 `22 × 2048 × 4 = 180224` 字节（176 KiB），虚拟页每页 8 KiB；
SDK 从实际 UICR Bootloader 地址向下分配。若实机 Bootloader 地址是源码中的 `0xF3000`，
FDS 位于 `[0xC7000, 0xF3000)`。其中一个虚拟页用于 GC 交换，21 页存数据，
扣除每页 8 字节页标签后，数据区为 171864 字节。没有读取实机 UICR，因此上述地址属于源码布局核算。
应用链接器上限收紧到 `0xC7000`，防止未来应用扩大后侵入现有 FDS；起始地址没有改变。

下表包含最大当前格式、4 字节对齐和每条记录 12 字节 FDS 头：

| 记录 | 最坏数量 × 单条物理长度 | 总字节 |
|---|---:|---:|
| HF 槽缓冲 | 16 × (4500 + 12) | 72192 |
| LF 槽缓冲 | 16 × (20 + 12) | 512 |
| HF/LF 槽昵称 | 32 × (36 + 12) | 1536 |
| 槽配置 v10 | 132 + 12 | 144 |
| 设置 | 16 + 12 | 28 |
| 全部现有槽及配置上限 | | 74412 |
| 日志 | 7 × (1024 + 12) | 7252 |

日志不占用新的原始地址，以独立 FDS file ID `0x1300`、keys `1..7` 写入。
每个会话 1024 字节，包含 32 字节管理信息、31 条 32 字节事件，CRC32 存在管理信息内。
将**完整 8192 字节 GC 交换页**及最坏七个所在页的 56 字节页标签也归入日志预算，
总预算 `7252 + 8192 + 56 = 15500` 字节，小于 16384 字节。
因此最终减少为 **7 个会话、最多 217 条事件**，没有采用 8 会话设计。
这不是独立物理分区；交换页由现有 FDS 共用，上述是对日志保守归因的上限。

不能只按字节空闲判断 FDS：4500 字节 HF 记录不能两条放入一个 8 KiB 页。
16 个最大 HF 槽至少占 16 数据页；小记录及日志保守另算 2 页，18/21 页，仍留 3 数据页，
足够正常最大槽记录的单次更新（另一个交换页用于 GC）。普通 FDS GC 会复制存活记录，
这是原有存储机制；没有人为搬迁槽分区、删除卡槽或缩减槽容量。
旧版本残留、Peer Manager 的配对/系统属性记录及更新产生的脏记录不属于上述固定槽上限，
它们会消耗其余空间，因此不承诺任意已有 FDS 都必然能写满七会话。
无法排队的保存报告失败并限频重试；已排队但完成失败的写入停止重试，避免积累残片。
重新开启前和清空后执行正常 FDS GC；不自动删除有效日志或任何有效卡数据。

RAM 两个 1024 字节缓冲（收集、读取校验），另有小量元数据。RF 回调不写 Flash。
新 RF 到来时若旧会话尚未保存则跳过，并报告溢出；容量满后不覆盖。
未保存的 RAM 会话在复位/断电时丢失。已保存记录在启动和读取时校验完整长度、字段边界和
CRC32（反射多项式 `0xEDB88320`，初值/最终异或 `0xFFFFFFFF`，CRC 字段按零计算）。
SDK FDS CRC 检查保持原配置关闭，避免改变旧数据的读取方式。
中断写入由 FDS 的提交标记/GC 和本模块 CRC 拒绝；实机电源切断尚未验证。

## DFU 边界

Bootloader 源码 `NRF_DFU_APP_DATA_AREA_SIZE=12288`，DFU 可用末地址为
`0xF3000 - 0x3000 = 0xF0000`，**这并不保留整个 176 KiB FDS**。
没有修改或刷入 Bootloader，也没有把应用未使用地址当日志区。
本包只包含 application，签名/哈希经过本地验证；它不能改变已安装 Bootloader 的擦除策略。
打包验证新增 320 KiB 应用上限：旧、新镜像都不超过 320 KiB 时，
双 bank 缓存末地址最多 `0x27000 + 0x50000 + 0x50000 = 0xC7000`，不触及 FDS。
该计算不能保证未知的已安装大镜像、单 bank 回退或其他 DFU/固件布局的保留。

只读查询实机得到 `Mocha-1.0.0-11211b3`、当前槽 6、轮询关闭；1120 返回旧固件 `0x67`。
本地同版本已存档应用镜像 309544 字节，其双 bank 起点为 `0x73000`。
版本字符串不是实机镜像哈希或 Bootloader 校验，因此不能作为完整 Flash 证明。
已只读备份槽 6 Classic 1K 的 1024 字节 dump 和模拟配置，未切槽、未写卡、未改轮询。
**其他 15 槽尚未备份，不满足完整刷入前备份条件。** 实机 UICR、Bootloader 行为及真实 DFU
保留均未验证。刷入前应完成用户审查、全槽备份和单独授权；本任务没有刷机或发布。

## CLI

关闭占用串口的 GUI，再用本机实际端口执行（端口可能变化）：

```sh
python3 tools/mocha.py --port /dev/cu.usbmodemEF1A1E2D3CC91 trace-status
python3 tools/mocha.py --port /dev/cu.usbmodemEF1A1E2D3CC91 trace on
python3 tools/mocha.py --port /dev/cu.usbmodemEF1A1E2D3CC91 trace off
python3 tools/mocha.py --port /dev/cu.usbmodemEF1A1E2D3CC91 trace-export trace.json
python3 tools/mocha.py --port /dev/cu.usbmodemEF1A1E2D3CC91 trace-export trace.csv --format csv
python3 tools/mocha.py --port /dev/cu.usbmodemEF1A1E2D3CC91 trace-clear --confirm
```

只导出已保存会话；分页变化时整个导出失败，不输出混合快照。
RF/保存期间不能切换开关。保存失败时允许显式清空，清空也会丢弃待保存 RAM。
清空成功前不会恢复正常深待机，CPU 仍能浅睡并响应 USB/BLE。
复现构建：设置 `GNU_INSTALL_ROOT` 和安装 requirements-build.txt 的 Python 后，运行
`tools/build_mocha.sh`；所有测试自动运行，构建不会刷机。

## v1.5 持久开关修复与实机更新

原先每次复位关闭是 volatile 开关策略；深待机复位因此也会关闭。
v1.5 用独立 FDS 0x1301/key1 的 16 字节 CRC32 控制记录保存开关，首次升级默认关闭。
不改变卡槽格式、设置、按钮映射和日志，恢复时不运行 GC 或反馈灯效。
仅在用户改变状态后、RF 离场及会话保存完成后写入；未保存时 status bit7 置位并阻止待机。
失败可见且不会伪称已保存，保存前突然断电仍可能恢复上一次持久状态。
旧/新控制记录及页标签也计入日志物理预算，保守合计 <=15600 字节，未超 16 KiB。
显式清空日志保留开关。详见协议 v1.5。

完整 Ultra 构建、21 项测试及 application-only DFU 验证通过，已更新设备为
`Mocha-1.0.0-fff0445-access-trace1.5`，features=127。
